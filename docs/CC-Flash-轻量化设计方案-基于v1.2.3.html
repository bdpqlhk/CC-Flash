01 · Diagnosis

v1.2.3 的“重”，还剩在哪里

不是代码质量差，而是主路径上堆了太多“顺手加的功能”。下面按模块拆开，只保留能直接服务“传文件 + 共享剪贴板”的部分。

App.vue 5.8k → 2.4k
server.rs 5.6k → 2.9k
style.css 3.2k → 1.2k
JS bundle 274KB → 190KB
.app 4.1MB → 3.5MB

注：v1.2.3 的具体行数/体积为本地实测基线；目标值为设计约束，不是精确承诺。实际收益取决于可选模块最终保留多少。

最大的一刀：聊天室。 时间线、Markdown、引用、未读、历史持久化、消息删除、文件组与聊天卡片交织在一起， 占了前端近三分之一的状态与样式。v1.2.3 的共享剪贴板已经落地，删除聊天室不会失去文字能力： 文字收敛成一格剪贴板，不再维护消息历史。
第二刀：浏览器设备发现。 v1.2.3 的浏览器仍会调用 /api/devices 并展示发现页， 但浏览器没有监听端口，永远无法作为可投递目标；让浏览器参与发现只会带来“看得到、连不上”的解释成本。 发现只保留在桌面端和手机 App。
02 · Architecture

一个内核，三种壳

桌面端与手机 App 共用同一个轻量 HTTP 内核；手机浏览器只是这个内核的静态页面客户端。发现能力只在内核的 App 侧启用。v1.2.3 已有共享剪贴板；App 最终收敛为「发送 / 设置」两标签，本方案主要把浏览器从发现链路摘出去，并删除聊天室。

Desktop · Tauri

桌面端：服务 + 发现 + 单页 UI

  • 启动即监听 HTTP，手机浏览器扫码/输地址即可用
  • 文件上传、下载、列表、删除、Range 续传
  • 共享剪贴板（GET/POST/DELETE + WS 事件）
  • UDP 发现：仅本 App 读取，不暴露给浏览器
  • 托盘 / 开机自启 / 单实例（平台基础能力）
Shared Core · axum

一个最小 HTTP 内核

  • files · upload · download · delete
  • clipboard · ws · info
  • 路径安全 / 并发闸 / 上传回滚（保留）
  • 可选：访问令牌、PWA、更新检查
⇄ HTTP / WS ⇅ UDP · App only
Mobile App · Tauri

手机 App：客户端 + 轻节点

  • 与桌面共用 HTTP 内核与文件/剪贴板 API
  • 参与 UDP 发现：可被桌面/其他 App 发现
  • 「发送 / 设置」两标签（最终落地；原方案曾设想三标签）
  • 默认独立轻节点（参与发现）；可切换「连接电脑」，切换后不参与发现
Mobile Browser · Static

手机浏览器：只做客户端

  • 单页：上传 / 文件列表 / 下载 / 共享剪贴板
  • 不调用发现接口，不显示附近设备
  • 不注册设备、不发 /api/hello
  • 无需安装，扫码或输入地址即用
浏览器永不进入发现列表 App 侧通过 Tauri 命令读取设备，不占用 HTTP 面 剪贴板是“一格文本”，不是聊天室 所有端共用同一套文件 API

04 · Minimal API

7 个端点，9 个方法，够用

浏览器只认文件与剪贴板；设备发现不进入 HTTP。这样既减少接口，也从协议层保证“浏览器不做发现”。v1.2.3 的 /api/clipboard 已存在；本方案删除 /api/hello、/api/devices 与 /api/chat*。

核心接口Keep
GET/api/info版本、端口、地址、运行状态、可选令牌开关
GET/api/files共享文件列表（递归、相对路径）
POST/api/upload单请求整文件直传（X-Filename / X-File-Size）
GET/api/download/{name}流式下载，支持 Range / 断点续传
DELETE/api/delete/{name}删除文件（路径越界校验）
GET/api/clipboard读取当前共享文本、来源、更新时间
POST/api/clipboard发布/覆盖共享文本（2 万字上限）
DELETE/api/clipboard清空共享文本
GET/wsfiles:changed / clipboard:changed 事件（可选，降级轮询）
移出 HTTP 面Remove
POST/api/hello浏览器不再上报设备；发现由 App 侧完成
GET/api/devices改为 Tauri 命令 list_devices_cmd，浏览器不可见
GET/api/chat聊天室删除；文字走剪贴板
POST/api/chat同上
DELETE/api/chat/{id}同上
POST/api/share-ticket核心不需要；分享=地址+可选令牌
App 侧发现数据流：UDP 线程维护内存设备表 → Tauri 命令 list_devices_cmd → App UI。 浏览器页面没有这条命令的通道，因此天然看不到附近设备，不需要额外分支判断。
请求/响应约定Lean
上传

单请求整文件直传；X-Filename URL 编码；同名自动 (1) 顺延；失败回滚半截文件。 不引入分片/断点协议，减少状态。

下载

GET 流式 + Range；浏览器原生下载器负责进度与续传；服务端只做文件流和越界校验。

剪贴板

单值模型：{ text, from, updatedAt }；POST 覆盖、DELETE 清空；WS 广播变更，无历史、无消息 ID。

08 · Trade-offs

删掉的东西，怎么补

轻量化必然有取舍。关键不是“删了会不会有人用”，而是“用最低成本给出一条替代路径”。

!
聊天室被删除

v1.2.3 的共享剪贴板已经落地，替代路径已就绪：一格文本 + “发布到剪贴板”按钮；需要长文时走文件传输。若确有需求，把聊天作为独立可选模块，不回到主路径。

!
浏览器不再发现设备

这是有意为之：浏览器没有监听端口，发现也投递不到。替代：桌面/App 显示二维码，浏览器扫码连接；浏览器只做文件与剪贴板。

!
主题与悬浮码的“精致感”下降

保留亮/暗与一个品牌色，视觉仍然统一；悬浮码改为顶栏二维码弹窗，减少一个独立窗口和一套窗口几何逻辑。

!
安全不能被“轻量”掉

路径穿越、上传大小/磁盘预检、上传回滚、并发闸、可选访问令牌必须保留；分享票据可以移出核心，但“地址 + 令牌”的底线不能丢。

!
迁移期数据

文件与剪贴板天然兼容；聊天历史不再进入新版本。升级时保留旧文件目录，剪贴板为空即可，不做消息迁移。

09 · Conclusion

一句话版本

把 CC-Flash 从“局域网聊天室”收回到“局域网文件 + 剪贴板工具”，设备发现只留给真正有监听端口的 App。

桌面端启动服务，手机浏览器扫码即传文件、共享剪贴板；发现只在桌面端和手机 App。 核心接口 7 个，核心页面 3 种，核心状态 2 个（文件 + 剪贴板）。 v1.2.3 的共享剪贴板、App 三标签、按需二维码与资源压缩全部保留；只删掉聊天室、浏览器发现和装饰性模块，代码量与首屏负担就会回到一个“工具该有的样子”。

核心 文件 + 剪贴板 发现 仅 App 浏览器 零安装客户端
CC Flash · 轻量化设计方案 · 基于 v1.2.3 · 2026-11-18 目标：更少的代码、更短的路径、更轻的常驻负担。

最终落地修正（以 v1.2.3 代码为准）

  • 聊天室保留：用户明确要求不删除聊天室；文件、消息、剪贴板共用同一条时间线。本方案中「移除聊天室、把文字收敛成一格剪贴板」未采纳。
  • 手机 App 两标签：最终只有「发送 / 设置」，不是「传输 / 发现 / 设置」三标签；发现并进发送页的目标横条 + 设备面板。
  • 桌面不再有独立「周边设备」入口：设备栏并入「消息发送」页左侧（200px），底部只保留刷新，不再重复二维码 / 复制地址。
  • 浏览器：保持原聊天室单页，不调用 /api/devices、不发 /api/hello、无底部标签与设置页——这部分按方案落地。
  • 共享剪贴板：双向、无开关、无独立模块，只在页面可见时同步；浏览器回退到「粘贴」面板。
